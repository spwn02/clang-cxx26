1. Introduction and motivation

P4380R1 describes expression macros that receive and return token sequences. A macro can therefore accept text whose grammar is not C++, such as markup in an html!-style invocation. The editor sees the raw argument tokens, but ordinary C++ parsing cannot assign useful C++ semantic colors or context-specific completion candidates to DSL tokens that the macro consumes.

Some editor support already follows from the macro expansion: when raw argument tokens are injected into a C++ expansion, ordinary C++ completion can occur in that expansion context. The fork also provides navigation into quote bodies. Those facilities do not address raw DSL text that is dropped or transformed before it forms C++ syntax. This paper proposes a narrow channel for macro-authored token roles and completion candidates, with no change to program translation.

These are editor hints. A compiler that does not provide an IDE interface can treat the role and candidate functions as no-ops; in such an implementation a completion token is never present in the macro's input.

2. Design

2.1 Token roles for highlighting

A macro may associate a token or token range with a role consisting of a kind and a set of modifiers. Roles help an editor highlight a DSL token as a type, property, parameter, or another supported semantic category. They do not affect parsing, constant evaluation, diagnostics, or the expansion result.

Only roles from a final successful expansion are eligible for presentation. If distinct expansions assign different kinds or modifier sets to the same source token, an editor should drop that token's role rather than choose one interpretation. Role data attached to source tokens that are unavailable to the editor may simply be ignored. These rules keep the displayed role tied to the expansion that actually supplied the program text.

2.2 Macro-supplied completion

During an editor completion request, the macro can recognize a distinguished completion token in its raw argument. A dedicated predicate distinguishes it from ordinary tokens. The macro may then publish candidates containing a display label, inserted text, kind, optional detail, and optional documentation. Candidate generation is macro-authored: the implementation does not infer the grammar of the DSL.

The editor replaces the identifier prefix immediately before the cursor. Therefore, for a cursor in data-f^, a candidate that inserts data-foo should publish foo as its insertion text. A candidate's label can remain data-foo. The location of the completion token selects which candidates apply; an implementation may impose per-expansion, per-request, and text-size caps.

Completion inside string literals and comments is not required by this proposal. The fork implementation stops raw-argument lexing before the closing delimiter in these positions, so the macro does not receive a completion token there. This limitation is an implementation observation and a recommended initial scope for the wording.

2.3 Example

This example uses the fork's current private API spelling. At an editor cursor in the raw html! argument, the macro can assign a property role and publish attribute candidates. In an ordinary compilation, the completion token and candidate calls have no translation effect.

#include <__meta/token_locations.h>
namespace mx = std::meta::__x;
using std::meta::token_sequence;

__macro html(token_sequence raw) {
  for (std::meta::token t : raw) {
    (void)mx::__role(t, mx::__semantic_token_kind::field);
    if (mx::__is_completion(t)) {
      (void)mx::__complete(t, "class", "class",
                           mx::__completion_kind::property,
                           "HTML attribute", "Class attribute");
      (void)mx::__complete(t, "className", "className",
                           mx::__completion_kind::property,
                           "HTML attribute", "Class name attribute");
    }
  }
  return ^^{ };
}
void render() { html!( <div cla> ); }

2.4 Specification strategy

The normative core should be small: define the role and completion functions, and state that their effect is implementation-defined editor hints with no effect on translation. The standard should not require a particular editor protocol, semantic-token encoding, candidate ranking algorithm, or markup grammar. Recommended practice and a quality-of-implementation note can describe how tools expose roles and merge candidates.

A non-IDE implementation conforms by making the functions no-ops for translation and by never supplying a completion token. It need not implement an editor transport or candidate UI.

2.5 Design alternatives

AlternativeReason not selected
LSP-side grammar plugins, such as a separate grammar provider for macro DSLs.This puts knowledge of each macro's language outside the macro definition and requires a second mapping from DSL source ranges to macro arguments. A macro-authored hint keeps the semantic choice with the code that recognizes the DSL.
A separate IDE query function exported by each macro.This creates a second macro interface and query lifecycle, separate from normal macro evaluation. It also needs a way to keep query results aligned with the exact current token sequence and cursor.
Attributes on declarations or tokens.Attributes can describe C++ entities, but raw DSL tokens may not become declarations or AST nodes. An attribute mechanism does not by itself carry completion candidates for a transient cursor in raw input.

3. Proposed wording

Draft wording relative to P4380R1. Bracketed labels are placeholders for clause placement and numbering. The interfaces below are examples of the proposed standard API; names and enum stability remain open.

[library] Editor role hints

namespace std::meta {
  enum class editor_role_kind : unsigned char;
  enum class editor_role_modifier : unsigned;
  consteval bool editor_role(token, editor_role_kind,
                             editor_role_modifier = {});
  consteval bool editor_role(token, token, editor_role_kind,
                             editor_role_modifier = {});
}

Effects: These functions provide implementation-defined editor hints and have no effect on translation. A role designates one token or the inclusive token range from the first argument through the second. The set and interpretation of role kinds and modifiers are implementation-defined.

[library] Completion candidates

namespace std::meta {
  enum class completion_kind : unsigned char;
  consteval bool is_completion_token(token);
  consteval bool editor_completion(token, string_view label,
                                   string_view insert_text,
                                   completion_kind = {},
                                   string_view detail = {},
                                   string_view documentation = {});
}

Effects: These functions provide implementation-defined editor hints and have no effect on translation. is_completion_token returns true only for the distinguished token representing the active completion position, if one is supplied. editor_completion makes the supplied candidate available to an implementation-defined editor interface for the completion request containing that token. Implementations may bound the number and size of candidates.

[recommended practice] Editor presentation

  • An implementation should expose roles only for the final successful expansion that produced them.
  • If successful expansions give conflicting roles to the same source token, an implementation should omit the role for that token.
  • An implementation should not expose role or completion hints from an expansion that fails.
  • A completion UI should replace the identifier prefix before the cursor with insert_text, while showing label as the candidate label. The implementation should preserve ordinary C++ completion results when it also presents macro-supplied candidates.
  • Implementations may omit candidates whose location or text exceeds implementation-defined limits. Completion inside a string literal or comment is not required.

[note] Non-editor implementations

An implementation without an editor interface can make the hint functions have no effect on translation. Such an implementation need not create a distinguished completion token.

4. Implementation experience

Fork implementation, not proposed wording: the fork declares its current APIs in <__meta/token_locations.h>, in reserved namespace std::meta::__x. Role APIs are named __role; role kinds and modifiers use private enums. Completion uses __is_completion, __complete, and __completion_kind. This spelling and transport are not proposed for standard wording.

In the fork, clangd receives roles through private remark diagnostics that it intercepts and hides. It applies roles only for successful expansions. If different expansions assign conflicting roles to one token, clangd drops that role. A fatal error suppresses role hints, and role data on tokens stored in PCH files or named modules is not shown. Roles for tokens outside the main file are ignored for main-file highlighting.

Candidate strings (label, insert text, detail, documentation) may be computed constant strings, for example generated from a data table in the macro body; they need not be string literals.

Macro-supplied completion is collected during a completion parse and merged into the editor result. The fork caps candidates at 128 per expansion and 512 per request; labels at 256 bytes, insertion text at 4096 bytes, detail at 1024 bytes, documentation at 4096 bytes, and total copied text at 64 KiB. Display strings can be truncated at UTF-8 boundaries; insertion text over its limit is discarded. The editor replaces the identifier prefix preceding the cursor. Candidates are unavailable inside string literals and comments. A completion request reaching clangd before the file's first preamble has been built may return only ordinary candidates.

The implementation's replay and tests cover a raw HTML-like argument, role conflict and failure cases, injected-token completion, and DSL completion that drops the completion token from C++ output. On the implementing commit the full gate reported 23 replay scenarios with 0 failures; 1476 clangd unit tests; 46,033 Clang tests passing (one further test failed and was fixed by updating its list of expected warning-group names); and an LSP stress run of 60 iterations with 3456 navigation and 1902 completion requests and 0 failures. The cc1 injection-loop result is 21800 runs with 0 failures. These figures are test results, not measurements of editor latency, adoption, or user benefit; those outcomes were not measured.

The transport, diagnostic interception, and clangd merge described above are implementation experience only. They are explicitly not part of the proposed wording.

5. Open questions and polls

  • Enum stability: Should role and completion kinds be implementation-defined, or should the standard define a stable common set with an extension mechanism?
  • Names: Are editor_role, is_completion_token, and editor_completion suitable names, or should these facilities live under a different reflection-library naming scheme?
  • Role scope: Should a role be permitted on a token that the successful expansion also uses in its returned C++ tokens, or only on tokens whose editor meaning differs from the generated C++ meaning?
  • Conflicts: Should conflicting roles from successful expansions be dropped, combined, or resolved by a specified precedence rule?
  • Candidate limits: Should the standard specify any upper bounds, or leave all limits to implementations and recommended practice?
  • Candidate scope: Should completion candidates from nested successful expansions be combined when they refer to the same cursor?
  • Poll: Do we want standard facilities for token roles and macro-supplied completion as implementation-defined editor hints?
