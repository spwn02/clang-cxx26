1. Introduction and motivation

P4380R1 describes function-shaped expression macros that receive token sequences and return token sequences. Its examples use std::constexpr_error_str in macro bodies, and its check! example places a diagnostic caret under an argument token. The design paper says that errors in injected tokens still point to the correct location, but it does not specify a diagnostic-location API or the interaction between such a diagnostic and macro expansion.

P2758R5 gives std::constexpr_error_str an effect during constant evaluation: it issues a diagnostic message and makes evaluation constexpr-erroneous. The associated wording says a constexpr-erroneous expression evaluated in a manifestly constant-evaluated context makes the program ill-formed, while the expression remains a core constant expression. That wording does not specify halting, a source location, or how multiple messages from one evaluation are reported. The message has no location component; tag strings support suppression or elevation.

This paper proposes separate facilities for token-location queries and for diagnostics attached to macro input tokens. A macro can identify the source spelling that needs attention, report more than one issue in a single evaluation, and optionally offer a source edit. A located error is accumulated while the macro body continues; once evaluation completes, the expansion fails and its returned tokens are discarded. This avoids using an invalid expansion as a continuation after an error.

The proposal is relative to P4380R1 and P2758R5 as design baselines. It does not amend the semantics of std::constexpr_error_str.

2. Design

2.1 Token locations

The proposed library queries return source locations for the beginning and exclusive end of a token, and for the beginning and exclusive end of a token range. A token without a source location yields a default source_location. For a diagnostic whose token location is absent or unusable, the diagnostic is attributed to the expression-macro invocation. For an end position whose token length was not retained by PCH or module serialization, an implementation may recover the end from a recoverable spelling; this is a quality-of-implementation choice, not a portable promise about exact columns.

2.2 Located reporting and evaluation

A macro can report an error, warning, or note on one token or an inclusive token range. A report can carry one optional fix-it: replace an inclusive token range, insert text after a token, or remove an inclusive token range. An implementation may discard a fix-it when its target is macro-produced or injected storage and cannot be represented as a safe file edit; the diagnostic itself remains.

Each report records a diagnostic and does not itself terminate evaluation. Evaluation continues through later executed statements in the macro body. At completion, if at least one located error was recorded, the expansion fails and all returned expansion tokens are discarded. The implementation reports the recorded located diagnostics without an additional generic expansion-failure cascade. Warnings and notes alone do not fail the expansion. Ordinary evaluation failures retain their ordinary behavior; the continuation guarantee here concerns located error reports.

These facilities have effect only during non-speculative evaluation of an expression-macro body. A speculative evaluation records no diagnostic. Evaluating a call to one of these facilities outside an expression-macro body is ill-formed. A report referring to a token with no usable location falls back to the macro invocation.

2.3 Interaction with P2758R5

std::constexpr_error_str remains as specified by P2758R5: it makes constant evaluation constexpr-erroneous and supplies a message without a token location. It is not converted into a located report. Because the call is constexpr-erroneous but still a core constant expression, evaluation of the macro body continues after it (the fork does so, and the expansion then fails with every message issued); this is consistent with the paper's ranges::begin example comment that the error "produces no expansion". A macro may use either facility, but a P2758 message does not acquire a location merely because the call appears in a macro body.

2.4 Design alternatives

AlternativeReason not selected
Add an optional location argument to constexpr_error_str.This couples a message facility whose P2758 semantics are constexpr-error based to token ownership and macro-specific buffering. It also leaves warning/note severities, fix-its, and multi-message continuation unresolved.
Return a diagnostic list from a macro.This changes the macro result shape and makes diagnostics a second output protocol every macro caller must handle. It also separates the reported source token from the evaluation that produced it.
Use tag strings to classify located reports.P2758 tag strings support diagnostic suppression or elevation but do not identify a token or source range. Encoding location or edit information in tags would give them unrelated responsibilities.
Throw an exception, following an exception-based diagnostic design such as P3068.An exception aborts the current evaluation path and cannot naturally accumulate several independent token diagnostics before the expansion is discarded. The proposal instead requires continued evaluation after a located error.

2.5 Example

The following uses the fork's current spelling to illustrate the proposed behavior. The invocation is intentionally diagnosed; the caret and replacement target the misspelled input token.

#include <__meta/token_locations.h>
using std::meta::token_sequence;
namespace mx = std::meta::__x;

__macro check_width(token_sequence ts) {
  (void)mx::__error(ts[0], "unknown attribute; did you mean 'width'?",
                    mx::__replace(ts[0], ts[0], "width"));
  return ^^{ \(ts) };
}
int value = check_width!(widht);

The proposed standard names below are illustrative and do not match the fork's reserved-name extension.

2.6 Example: a try_-style misuse check

P4380R1's try_ example reports misuse with std::constexpr_error_str, which has no location. With located reports the same kind of check can point at the offending argument tokens and offer a note, and the macro keeps evaluating after the first report.

#include <__meta/token_locations.h>
using std::meta::token_sequence;
namespace mx = std::meta::__x;
__macro try_value(token_sequence ts) {
  if (ts.size() != 1) {
    mx::__error(ts[0], ts[ts.size() - 1], "try_value! expects exactly one token");
    mx::__note(ts[0], "wrap the expression in parentheses");
    return ^^{ 0 };
  }
  return ^^{ \(ts) };
}
int a = try_value!(1 + 2);

In the fork this reports the error at the first token of the argument (1), with a note at the same token, and no further diagnostic such as "did not produce a token sequence"; the 0 is never injected.

3. Proposed wording

Draft wording relative to P4380R1 and P2758R5. Bracketed labels are placeholders for clause placement and numbering.

[library] Token source locations

Add declarations to the reflection library synopsis:

namespace std::meta {
  consteval source_location token_location_begin(token);
  consteval source_location token_location_end(token);
  consteval source_location token_range_location_begin(token, token);
  consteval source_location token_range_location_end(token, token);
}

Mandates: The first and last arguments to a range query designate the first and last tokens of an inclusive token range. Returns: The source location of the beginning or exclusive end of the designated spelling. If a token has no source location, returns a default-initialized source_location. An implementation is encouraged to recover an end location when serialized token length is unavailable and the spelling can be recovered.

[library] Reporting a diagnostic

Add the following declarations to the reflection library synopsis. The fix-it descriptor is exposition-only here; the final API shape is an open question.

namespace std::meta {
  struct diagnostic_fixit {
    enum class kind { replace, insert_after, remove };
    kind operation;
    token first;
    token last;
    string_view replacement;
  };

  consteval diagnostic_fixit replace_tokens(token, token, string_view);
  consteval diagnostic_fixit insert_after(token, string_view);
  consteval diagnostic_fixit remove_tokens(token, token);

  consteval bool report_error(token, string_view, diagnostic_fixit = {});
  consteval bool report_error(token, token, string_view, diagnostic_fixit = {});
  consteval bool report_warning(token, string_view, diagnostic_fixit = {});
  consteval bool report_warning(token, token, string_view, diagnostic_fixit = {});
  consteval bool report_note(token, string_view, diagnostic_fixit = {});
  consteval bool report_note(token, token, string_view, diagnostic_fixit = {});
}

Mandates: These functions are evaluated only as part of evaluation of an expression-macro body. Otherwise, the program is ill-formed. A call during speculative evaluation has no effect. Effects: Each call records one diagnostic of the specified severity and message, associated with the designated token or inclusive token range. If that designation has no usable source location, the diagnostic is associated with the expression-macro invocation. A fix-it is a request to replace or remove the designated inclusive token range, or to insert after the designated token; an implementation may omit a fix-it it cannot apply to source text.

Evaluation: Evaluation of the macro body continues after a call to report_error. If evaluation completes and one or more error diagnostics were recorded, the macro expansion fails and no tokens are injected from that expansion. The implementation emits the recorded diagnostics and does not emit a further diagnostic solely because the expansion failed. If no error diagnostic was recorded, the expansion result is processed as otherwise specified. A warning or note alone does not cause failure.

[expr.const] Relationship to constexpr messages

No change is proposed to the P2758R5 wording or semantics of std::constexpr_error_str. The location-aware functions above are distinct operations; a call to std::constexpr_error_str does not designate a token location.

4. Implementation experience

Fork implementation, not proposed wording: the current implementation exposes the functions through <__meta/token_locations.h> in reserved namespace std::meta::__x, with double-underscore names such as __token_begin, __error, and __replace. The header is C++29-only and is not exported by <meta> or import std;. The proposed standard API above deliberately uses non-reserved names.

In the fork, the message and the fix-it replacement text may be any constant string, including one computed in the macro body (a std::string built there, an element of a constexpr table); the compiler reads the characters through the constant evaluator, so the strings need not be literals. A string that cannot be read is diagnosed at the macro author's token and names the argument. Each byte is read through one constant-evaluation step, so string size is also bounded by the evaluator's step limit; the fork additionally caps messages and fix-it text at 4096 bytes (a longer message is truncated, a longer replacement drops the fix-it).

In the fork, a missing token location produces a default location for location queries, while an invalid diagnostic location falls back to the macro call. Token-end recovery after PCH/module serialization uses a recoverable spelling when possible; the fork's test describes serialized non-literal token lengths as unavailable. Exact token-end recovery across serialization is therefore implementation quality, not a portable guarantee. Fix-its are discarded when the target is macro-produced or injected storage.

The fork's regression cases exercise one error, two errors in a single expansion, warning and note, invalid-location fallback, replace/insert/remove edits, rejected edits in macro storage, macros inside templates (behaviour unchanged), and the legacy message path (evaluation continues after it and the expansion then fails). In its test, the legacy call still diagnoses expression macro 'legacy_error' reported an error at the invocation and carries its message note.

On the implementing commit the full gate reported: 23 clangd replay scenarios with 0 failures; 1476 clangd unit tests; 46,033 Clang tests passing (one further test failed and was fixed by updating its list of expected warning-group names); an LSP stress run of 60 iterations with 3456 navigation and 1902 completion requests and 0 failures; and 21800 cc1 injection-loop runs with 0 failures. These are test results, not performance measurements or evidence of user outcomes. Timing and broader user impact were not measured.

5. Open questions and polls

  • API naming: Should the standard use token_location_begin/token_location_end and report_error/report_warning/report_note, or names closer to the fork spellings?
  • Fix-it type: Should replace, insert-after, and remove be represented by one descriptor, overloads, or a smaller initial API? Should range endpoints be spelled as a token range abstraction rather than two tokens?
  • Location fallback: Is invocation fallback the right specified behavior for an unlocated token, or should the API require the caller to supply an explicit fallback?
  • Serialization: Should token end locations be specified only as an implementation quality, given that serialized token lengths may be unavailable?
  • Error continuation: Is continuing macro-body evaluation after a located error, then failing the expansion once the body completes, the desired rule?
  • Poll: Do we want to pursue the token-location and located-diagnostic facility for expression macros?
